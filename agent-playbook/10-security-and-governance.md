# 10. Security and governance

Execution class determines how work runs. The governance tier determines how
rigorously the agent must be governed.

## Governance tiers

Use the [agent risk-assessment standard](13-risk-assessment.md) to identify harm
scenarios across eight dimensions, score inherent and residual risk, apply
mandatory floors, link controls to evidence, and record acceptance. The Agent
Spec declares the assessment's governance tier. The highest material
scenario determines the tier; dimensions and scenarios MUST NOT be averaged.

| Tier     | Typical controls                                                                                             |
| -------- | ------------------------------------------------------------------------------------------------------------ |
| Low      | Owner, typed contract, smoke evals, budgets, telemetry, peer review                                          |
| Medium   | Risk assessment, regression/safety/trajectory evals, staged deployment, domain review                        |
| High     | Threat model, security/privacy review, human governance, adversarial evals, audit, canary                    |
| Critical | Independent assessment, dual control where appropriate, continuous eval, kill switch, formal recertification |

Some uses remain prohibited even with added controls.

## Ownership

Every agent names product, engineering, quality, operational, domain, and applicable security owners. One person may fill multiple roles, but accountability MUST be explicit.

## Threat model

Medium-, high-, and critical-risk agents maintain a threat model covering users, trust boundaries, providers, tools, MCP, skills, retrieval, memory, durable execution, approval, telemetry, audit, deployment, and dependencies.

At minimum, consider:

- Goal hijacking and indirect prompt injection
- Tool misuse and excessive agency
- Identity or privilege abuse
- Cross-tenant access and sensitive-data disclosure
- Memory, skill, or prompt poisoning
- MCP and dependency compromise
- Unexpected code execution
- Denial of wallet
- Approval forgery or replay
- Duplicate side effects
- Telemetry or audit evasion

For each material threat, identify preventive, detective, and recovery controls.

## Identity and authorization

- Use least-privilege, environment-specific, preferably short-lived credentials.
- Propagate authenticated actor and tenant context.
- Enforce authorization deterministically at tool execution.
- Never accept identity, scope, or approval claims generated by the model.
- Recheck authorization immediately before side effects.
- Record the acting identity in audit events.

An agent or prompt is not a security principal.

## Untrusted content

Treat user input, retrieved documents, websites, emails, tool results, and external model output as untrusted data. Untrusted content cannot override system policy, grant authorization, expand capabilities, change execution class, approve actions, or reveal secrets.

Retrieved content SHOULD be clearly delimited and labeled as evidence rather than instruction.

## Secrets and data

Secrets come from an approved manager and appear only where needed. They MUST NOT appear in Agent Specs, skills, prompts, model-visible dependencies, workflow history, tool results, eval datasets, telemetry, or source control.

Minimize data before model submission. Provider, region, retention, and training-use policy MUST be approved for the data classification.

## MCP and supply chain

External capabilities require an owner, immutable identity or version, trust classification, authentication, egress rules, data classification, effect classification, dependency monitoring, and revocation process.

MCP servers MUST be allowlisted, authenticated, pinned where possible, and monitored for unexpected tool-list changes. Server descriptions and results are untrusted. Dynamic production installation is prohibited.

Agent frameworks, SDKs, and runtime libraries evolve quickly, and pre-1.0 releases may change behavior without notice. Production projects SHOULD pin versions, review release notes, and run full compatibility evals before upgrades, treating each upgrade as a behavioral change.

## Isolation

Production agents SHOULD use outbound network allowlists, restricted filesystems, immutable artifacts, resource limits, isolated temporary storage, and no ambient credentials. Arbitrary code execution is a distinct high-risk tool and requires a sandbox, quotas, and strong artifact controls.

## Change classes

| Change             | Additional requirements                                           |
| ------------------ | ----------------------------------------------------------------- |
| Non-behavioral     | Unit/static checks and peer review                                |
| Behavioral         | Agent version, offline evals, baseline comparison, staged rollout |
| Security-sensitive | Security review, adversarial evals, threat-model update           |
| Replay-sensitive   | Replay tests, code-versioning plan, compatible build retention    |

A change may belong to more than one class.

## Deployment

Use a risk-appropriate progression:

```text
local → integration → staging → shadow → canary → gradual rollout → full release
```

Shadow mode MUST disable side effects. Canary promotion depends on operational and behavioral health. Rollback plans MUST account for active workflow histories; keeping a build that can continue in-flight workflows may be necessary even after routing new work to an earlier build.

## Kill switches

Support authenticated, audited disabling of an agent, version, model, provider, skill, tool, tenant, workflow type, or new workflow starts. Durable controls distinguish stopping new work, pausing active work, cancelling it, allowing safe completion, and blocking the next side effect.

## Incident response

The runbook sequence is:

1. Contain.
2. Preserve evidence.
3. Identify affected manifests, workflows, tenants, and actions.
4. Revoke or restrict capabilities.
5. Stop or isolate unsafe workflows.
6. Compensate reversible effects.
7. Notify required stakeholders.
8. Add regression cases.
9. Correct and validate the system.
10. Complete a post-incident review.

## Exceptions and review

An exception records the waived requirement, justification, risk, compensating controls, approver, scope, expiry, and re-review date.

Suggested maximum review intervals are 12 months for low risk, 6 months for medium, 3 months for high, and 1 month for critical, adjusted for organizational and regulatory requirements.

## Decommissioning

Stop new starts, inventory active workflows, complete/cancel/migrate them, keep a compatible build available as required, revoke access, remove tool and MCP registrations, retain required audit and eval artifacts, delete data by policy, and mark the capability manifest retired.
