# Part 1 practical reference

**Status:** 0.5.0-draft.2 — proposed companion material, not adopted  
**Purpose:** Help a builder connect the four Part 1 planning records without creating a second set of requirements.  
**Use with:** The [Part 1 overview](../README.md), the named owner chapter, the [glossary pointers](../../../glossary.md#part-1-planning-foundations), and the [requirement index](../../../requirement-index.md#part-1--problem-definition-and-planning).

This reference owns no requirement IDs. The chapter owner, its applicability statement, and its `## Requirements` section control if a template field or this guidance is shorter than the proposed requirement.

## Build one planning packet in order

1. **Establish the user need and current work.** Use [1.1 Defining the Problem](../01-defining-the-problem.md) and the [problem brief](../../../templates/1.1/problem-brief.yaml). Carry forward the bounded task, evidence status, assumptions, scope, dependencies, and downstream consumer.
2. **State what a worthwhile result would mean.** Use [1.2 Requirements, Success Criteria, and Measurable Targets](../02-requirements-success-criteria-and-measurable-targets.md) and the [success-criteria record](../../../templates/1.2/success-criteria.yaml). Carry forward the outcome and acceptance logic, separate decision dimensions, baseline status, and evidence handoff.
3. **Compare the smallest plausible approaches.** Use [1.3 Agent Suitability and Alternatives](../03-agent-suitability-and-alternatives.md) and the [suitability decision](../../../templates/1.3/suitability-decision.yaml). Carry forward the shared task cases, simpler baseline, rationale, uncertainty, and any unproven added-value claim.
4. **Screen early conditions and route unresolved work.** Use [1.4 Initial Risk, Data, Ownership, and Delivery Plan](../04-initial-risk-data-ownership-and-delivery-plan.md) and the [initial scope record](../../../templates/1.4/initial-scope-record.yaml). Carry forward harm and affected-person questions, source/access and capability facts, owners, applicability, containment/restart questions, and specialist handoffs.

The four templates use a connected illustrative planning identity. Treat their fixture values, unknowns, and planned fields as structure for a record—not as observations, measured results, approvals, or a production design.

## Practical use and review

1. **Keep evidence status visible.** Reported difficulty, an assumption, a planned target, and an observed result answer different questions; do not promote one into another while copying a field between records.
2. **Keep the comparison fair.** Carry the same bounded task, source/access conditions, and material outcome claim from the brief into the suitability decision. A fixed workflow can remain the preferred provisional option.
3. **Make unknowns a handoff, not a pass.** Use the scope record to name the owner and the next applicable Part when risk, data handling, authority, evidence, rollout, or execution detail is unresolved.
4. **Use later Parts for proof and authorization.** [Part 4](../../04-testing-and-evaluation/README.md) designs evidence; [Part 5](../../05-release-operations-and-lifecycle/README.md) addresses release and operations. Neither a completed template nor an evaluation conclusion is deployment authorization.

For terminology, read the chapter-local explanation at the decision point and use the [glossary](../../../glossary.md) only as a navigation aid. For triggered capability, security, execution, or specialized-assurance work, follow [applicability](../../../applicability.md) rather than inferring that every reference mechanism applies.
