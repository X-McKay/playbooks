## Terms

- **Adaptive agent:** An agent whose model may select or change next actions in response to observations within declared controls. Conditional branching alone does not make a fixed workflow adaptive. See [1.3](development-guide/01-problem-definition-and-planning/03-agent-suitability-and-alternatives.md).
- **Agent:** A bounded system that combines a model with instructions, context, state, and admitted capabilities to produce contract-defined outcomes. See [2.1](development-guide/02-agent-basics/01-agent-anatomy-runtime-loop-and-project-organization.md) and [2.2](development-guide/02-agent-basics/02-agent-contracts-and-configuration.md).
- **Approval:** An authenticated, in-scope decision on an immutable action subject. It is an additional condition, not a source of authority. See [7.3](engineering-reference/07-durable-execution-and-human-governed-work/03-approval-suspension-and-in-flight-compatibility.md).
- **Authoritative state observation:** A trusted, identified observation of relevant state or effect used to establish that an action occurred, did not occur, or left an unknown outcome. A transcript is not an authoritative state observation. See [4.1](development-guide/04-testing-and-evaluation/01-foundations-terms-and-definitions.md) and [4.4](development-guide/04-testing-and-evaluation/04-evaluators-metrics-rubrics-and-calibration.md).
- **Authorization:** A deterministic decision at a protected-operation boundary using trusted identity, action, resource, and scope. See [3.1](development-guide/03-security-and-trust-boundaries/01-identity-authority-zero-trust-and-least-privilege.md).
- **Baseline:** The identified comparator used to interpret a candidate change; a first release may have no prior deployed baseline but still needs decision-grade evidence. See [1.3](development-guide/01-problem-definition-and-planning/03-agent-suitability-and-alternatives.md) and [4.7](development-guide/04-testing-and-evaluation/07-analyzing-results-comparing-versions-and-making-decisions.md).
- **Bounded outcome:** A contract-defined response when work cannot safely complete, such as `needs_information`, `declined`, `failed`, escalation, or a declared partial result. See [2.2](development-guide/02-agent-basics/02-agent-contracts-and-configuration.md) and [4.3](development-guide/04-testing-and-evaluation/03-evaluation-types-and-dimensions.md).
- **Candidate:** The exact version/configuration, allowed capability set, source policy, and relevant routing/fallback combination being evaluated or released. See [4.7](development-guide/04-testing-and-evaluation/07-analyzing-results-comparing-versions-and-making-decisions.md).
- **Capability:** An admitted model, skill, retrieval source, tool, or other runtime facility available to an agent. Discovery or package presence does not grant permission. See [2.2](development-guide/02-agent-basics/02-agent-contracts-and-configuration.md).
- **Capability manifest:** The immutable or digest-bound identity of the effective declared configuration and capability set, linked to evaluation and runtime evidence. See [2.2](development-guide/02-agent-basics/02-agent-contracts-and-configuration.md).
- **Case:** A versioned bounded task or probe with inputs, relevant conditions, expected observable outcome or invariants, permitted variation, and origin/rationale. It is not only a prompt and preferred response. See [4.1](development-guide/04-testing-and-evaluation/01-foundations-terms-and-definitions.md) and [4.5](development-guide/04-testing-and-evaluation/05-planning-designing-and-running-tests-and-evaluations.md).
- **Compaction:** Replacing older context with a shorter summary so a long-running agent stays within its context budget, while keeping protected facts such as constraints and identities intact. See [8.2](engineering-reference/08-model-context-and-resource-engineering/02-retrieval-memory-and-context-optimization.md).
- **Conditional_go:** A narrowly permitted evaluation conclusion after required pre-release evidence and controls are met, with bounded post-release obligations. It is not a waiver for missing required evidence or deployment authorization. See [4.7](development-guide/04-testing-and-evaluation/07-analyzing-results-comparing-versions-and-making-decisions.md) and [5.2](development-guide/05-release-operations-and-lifecycle/02-readiness-change-and-rollout.md).
- **Consequential action:** An external effect whose consequence requires human-governed approval under the applicable policy; it also requires independent authorization. See [7.1](engineering-reference/07-durable-execution-and-human-governed-work/01-execution-classes-persistence-and-recovery.md).
- **Control:** A preventive, detective, or recovery measure that receives risk-reduction credit only when evidence supports its design and operation. See [10.1](engineering-reference/10-risk-privacy-and-specialized-assurance/01-detailed-risk-assessment-and-governance.md).
- **Durable execution:** Persisted workflow execution that can recover/resume under declared replay, state, and recovery rules. It does not prove exactly-once external effects. See [7.1](engineering-reference/07-durable-execution-and-human-governed-work/01-execution-classes-persistence-and-recovery.md).
- **Effect / external effect:** A change visible outside the agent boundary. It needs declared retry/reconciliation handling; a missing receipt is not proof that no effect occurred. See [7.2](engineering-reference/07-durable-execution-and-human-governed-work/02-side-effects-idempotency-and-unknown-outcomes.md).
- **Evaluator:** The versioned rule, procedure, instrument, or qualified role that turns stated evidence into an observation or judgment. It is distinct from the evidence source and the metric that summarizes results. See [4.1](development-guide/04-testing-and-evaluation/01-foundations-terms-and-definitions.md) and [4.4](development-guide/04-testing-and-evaluation/04-evaluators-metrics-rubrics-and-calibration.md).
- **Evidence:** Identified observations, source/state records, evaluator results, and review records that establish a specific bounded claim. A fluent transcript, citation presence, or model assertion may be insufficient. See [4.1](development-guide/04-testing-and-evaluation/01-foundations-terms-and-definitions.md), [4.4](development-guide/04-testing-and-evaluation/04-evaluators-metrics-rubrics-and-calibration.md), and [4.5](development-guide/04-testing-and-evaluation/05-planning-designing-and-running-tests-and-evaluations.md).
- **Evidence source:** The identified thing inspected by an evaluator, such as source text, a permission decision, a controlled fixture, an authoritative state record, a reference label, or a response. It is not interchangeable with the evaluator or metric. See [4.4](development-guide/04-testing-and-evaluation/04-evaluators-metrics-rubrics-and-calibration.md).
- **Execution class:** How an agent run is executed and recovered: `ephemeral`, `durable`, or `human_governed`. It is separate from governance tier and residual risk. See [7.1](engineering-reference/07-durable-execution-and-human-governed-work/01-execution-classes-persistence-and-recovery.md).
- **Fixed-world repeated-run reliability:** The correctness-qualified result of freshly initialized episodes of the same identified case, fixture, permission context, and run policy. It is neither byte-for-byte sameness nor a population reliability estimate. See [4.3](development-guide/04-testing-and-evaluation/03-evaluation-types-and-dimensions.md).
- **Fixture:** Revisioned starting data, state, and dependency behavior needed to interpret a case, including isolation and reset where relevant. It establishes a controlled world; it is not automatically the rule that judges the outcome. See [4.1](development-guide/04-testing-and-evaluation/01-foundations-terms-and-definitions.md) and [4.5](development-guide/04-testing-and-evaluation/05-planning-designing-and-running-tests-and-evaluations.md).
- **Gate / hard gate:** A non-compensable decision condition. A favorable average, unrelated score, generic exception, or later selected retry cannot compensate for a failed applicable gate or missing required valid evidence. See [4.7](development-guide/04-testing-and-evaluation/07-analyzing-results-comparing-versions-and-making-decisions.md).
- **Governance tier:** The assurance and oversight level derived from the highest applicable inherent-risk scenario, policy, legal, or capability floor; it is not an execution class. See [10.1](engineering-reference/10-risk-privacy-and-specialized-assurance/01-detailed-risk-assessment-and-governance.md).
- **Governed exception:** A documented, authorized exception to an applicable requirement that policy explicitly marks exception-eligible. It never overrides a prohibited use, mandatory floor, required authorization, or non-waivable gate. See [5.2](development-guide/05-release-operations-and-lifecycle/02-readiness-change-and-rollout.md).
- **Holdout (release holdout):** A separately authored set of cases kept out of tuning, used to check a release decision. See [4.2](development-guide/04-testing-and-evaluation/02-test-levels-techniques-and-suite-purposes.md) and [4.7](development-guide/04-testing-and-evaluation/07-analyzing-results-comparing-versions-and-making-decisions.md).
- **Human-governed:** The execution class for consequential actions requiring an approval flow under policy, followed by execution-time authorization. See [7.1](engineering-reference/07-durable-execution-and-human-governed-work/01-execution-classes-persistence-and-recovery.md) and [7.3](engineering-reference/07-durable-execution-and-human-governed-work/03-approval-suspension-and-in-flight-compatibility.md).
- **Inconclusive / invalid:** **Invalid** means a declared condition prevents attribution to the candidate; **inconclusive** means a recorded execution does not establish the claim. Both remain visible and are not passes; missing required valid evidence is a decision-state finding. See [4.5](development-guide/04-testing-and-evaluation/05-planning-designing-and-running-tests-and-evaluations.md) and [4.7](development-guide/04-testing-and-evaluation/07-analyzing-results-comparing-versions-and-making-decisions.md).
- **Inherent risk / residual risk:** Risk before risk-reducing controls / risk after only evidenced controls. Neither term is interchangeable with governance tier. See [10.1](engineering-reference/10-risk-privacy-and-specialized-assurance/01-detailed-risk-assessment-and-governance.md).
- **Invariance relation:** A reviewed controlled change justified as irrelevant to a claim, for which the required outcome and controls must be preserved. It does not prove correctness by itself. See [4.3](development-guide/04-testing-and-evaluation/03-evaluation-types-and-dimensions.md).
- **MCP:** A standardized host/client/server integration protocol. Its use is optional; advertised or discovered capabilities still require admission and authorization. See [2.7](development-guide/02-agent-basics/07-mcp-and-standardized-integrations.md).
- **Metric:** A definition of what is measured and how observations are summarized. It is distinct from the evaluator/instrument and must use a denominator, attempt unit, status handling, and retry/selection policy that fit the claim. See [4.4](development-guide/04-testing-and-evaluation/04-evaluators-metrics-rubrics-and-calibration.md) and [4.7](development-guide/04-testing-and-evaluation/07-analyzing-results-comparing-versions-and-making-decisions.md).
- **Model policy:** The versioned logical rule for selecting a model/provider/deployment/settings; the resolved identity belongs in evidence and operations. See [8.1](engineering-reference/08-model-context-and-resource-engineering/01-model-selection-parameters-and-routing.md).
- **Not applicable with rationale:** A record that a requirement's trigger is absent for the reviewed candidate/scope. It is not an exception or pass for a triggered requirement. See [Applicability](applicability.md) and [4.6](development-guide/04-testing-and-evaluation/06-standards-required-coverage-and-execution-cadence.md).
- **Oracle / reference:** A named, claim-specific expected value, accepted alternative set, label, invariant, or trusted answer/state provider. Identify its role, authority, scope, time/version, and limits rather than treating “oracle” as a generic source. See [4.1](development-guide/04-testing-and-evaluation/01-foundations-terms-and-definitions.md) and [4.4](development-guide/04-testing-and-evaluation/04-evaluators-metrics-rubrics-and-calibration.md).
- **pass@k / pass^k:** pass@k asks whether at least one of k attempts succeeds; pass^k asks whether all k succeed, which is the better measure of consistency for user-facing agents. See [4.7](development-guide/04-testing-and-evaluation/07-analyzing-results-comparing-versions-and-making-decisions.md).
- **Physical attempt:** One actual call or execution, including retries and fallbacks that the user never sees. Costs, effects and failures are counted per physical attempt, not only for the result that was finally selected. See [4.7](development-guide/04-testing-and-evaluation/07-analyzing-results-comparing-versions-and-making-decisions.md).
- **Prompt injection:** Text in a request (direct) or in retrieved content, tool output or other data (indirect) that tries to change the agent's instructions or actions. Defend by design and at the action boundary, not by prompt wording alone. See [3.2](development-guide/03-security-and-trust-boundaries/02-untrusted-inputs-retrieved-content-and-action-boundaries.md).
- **Proposed action:** Structured candidate work awaiting deterministic validation, authorization, and where applicable approval. It is distinct from an action actually performed. See [2.2](development-guide/02-agent-basics/02-agent-contracts-and-configuration.md).
- **Provenance:** Enough identity, source/version/freshness, and context information to trace material evidence or data to its origin and permitted use. See [2.6](development-guide/02-agent-basics/06-context-and-retrieval-fundamentals.md) and [4.3](development-guide/04-testing-and-evaluation/03-evaluation-types-and-dimensions.md).
- **Reference answer / truth reference:** A reference answer expresses accepted results or invariants for a bounded case. An external factual-truth claim separately needs an independent authoritative truth reference with time context; source support alone may not establish it. See [4.4](development-guide/04-testing-and-evaluation/04-evaluators-metrics-rubrics-and-calibration.md).
- **Retry, selection, and final-result policy:** The declared operational rule for whether another physical attempt may occur, how it is made safe, how a result is chosen, and what reaches the user or downstream system. All physical attempts and applicable effects/costs remain evidence. See [4.7](development-guide/04-testing-and-evaluation/07-analyzing-results-comparing-versions-and-making-decisions.md).
- **Rule of Two / lethal trifecta:** A design rule: one session should not combine all three of untrusted input, access to sensitive data or systems, and the ability to change state or communicate externally without human approval. See [3.1](development-guide/03-security-and-trust-boundaries/01-identity-authority-zero-trust-and-least-privilege.md).
- **Sensitivity relation:** A reviewed controlled change that is material to a claim and must cause the contractually required change in answer, boundary decision, or uncertainty. It pairs with invariance so consistency does not reward ignoring context. See [4.3](development-guide/04-testing-and-evaluation/03-evaluation-types-and-dimensions.md).
- **Skill:** An optional focused reusable procedure/knowledge package. A skill, its prose, metadata, or bundled file cannot grant capability or authority. See [2.5](development-guide/02-agent-basics/05-skills-and-reusable-capabilities.md).
- **Source admission/currentness:** The distinct claim that a source is permitted for a requester/use and current at the relevant time. It is not semantic grounding, retrieval relevance, or external factual truth. See [4.3](development-guide/04-testing-and-evaluation/03-evaluation-types-and-dimensions.md) and [4.4](development-guide/04-testing-and-evaluation/04-evaluators-metrics-rubrics-and-calibration.md).
- **Suite:** A versioned set of cases selected for a stated coverage goal or purpose, such as development, regression, release holdout, acceptance, smoke, or operational learning. Purpose does not name the technical boundary. See [4.1](development-guide/04-testing-and-evaluation/01-foundations-terms-and-definitions.md) and [4.2](development-guide/04-testing-and-evaluation/02-test-levels-techniques-and-suite-purposes.md).
- **System Spec / composition manifest:** The versioned system-level contract and immutable composition identity for a multi-agent system; it does not silently override a member contract. See [9.1](engineering-reference/09-multi-agent-systems-and-interoperability/01-when-multiple-agents-help-topologies-and-system-contracts.md).
- **Terminal outcome:** One of the declared ways a run can end, such as `complete`, `needs_information`, `declined` or `failed`; the agent contract must cover at least these four. See [2.2](development-guide/02-agent-basics/02-agent-contracts-and-configuration.md).
- **Tool:** An admitted typed external interface with a declared effect, execution-class floor, validation, timeout, authorization, and retry behavior. See [2.4](development-guide/02-agent-basics/04-tools-and-external-interfaces.md).
- **Trajectory:** The claim-relevant, observable ordered or partially ordered event record, such as a request, boundary decision, source identity, response, and state/effect observation. It permits safe alternatives and does not require private chain-of-thought. See [4.1](development-guide/04-testing-and-evaluation/01-foundations-terms-and-definitions.md) and [4.3](development-guide/04-testing-and-evaluation/03-evaluation-types-and-dimensions.md).
- **Trial:** One recorded execution attempt of a case under an identified candidate/configuration and initial conditions. Trials may share conditions and are not automatically independent. See [4.1](development-guide/04-testing-and-evaluation/01-foundations-terms-and-definitions.md), [4.5](development-guide/04-testing-and-evaluation/05-planning-designing-and-running-tests-and-evaluations.md), and [4.7](development-guide/04-testing-and-evaluation/07-analyzing-results-comparing-versions-and-making-decisions.md).
- **Trusted context / untrusted content:** Identity, authority, policy, and scope must come from named trusted sources. User input, retrieved material, tool output, memory, and peer messages remain untrusted data. See [3.1](development-guide/03-security-and-trust-boundaries/01-identity-authority-zero-trust-and-least-privilege.md) and [3.2](development-guide/03-security-and-trust-boundaries/02-untrusted-inputs-retrieved-content-and-action-boundaries.md).
